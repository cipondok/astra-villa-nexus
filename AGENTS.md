# AGENTS.md

- Theme colors live only in the `:root` / `.dark` token blocks of `src/index.css` (HSL triplets) plus Tailwind aliases in `tailwind.config.ts`; why: one palette change must reach every route.
- REOS marketing surfaces (shell, homepage) read their CSS vars from the single `reosTokens` string exported by `src/components/reos/ReosShell.tsx`; why: duplicated per-page palettes drifted apart.
- The "matte finish" layer at the end of `src/index.css` neutralizes legacy glow/shimmer/glossy classes globally and must stay last in the file; why: legacy effect classes are spread across many pages.
- RLS helper functions that only gate policies live in the `private` schema (not exposed through the API); why: keeps internal access checks from being callable directly.
- On phones the REOS header shows only logo/wordmark plus round search, notifications and menu buttons; sign-in, account, navigation, language and theme live in the ReosHeader drawer (also opened by the bottom bar "Ecosystem" tab via `REOS_OPEN_MENU_EVENT`) and the bottom tab bar; app-sidebar routes (`/dashboard`, `/ai-center`, `/profile`…) also mount this header and bottom bar below `md` because their sidebar has no phone trigger; why: one mobile menu avoids clipped header controls and dead-end pages.
- Every sign-up, password-change and reset form validates through `src/lib/passwordPolicy.ts` (also enforced in `AuthContext.signUp`) and shows `PasswordStrengthBar`; why: one weak-password list and rule set instead of per-form checks.
- Property detail pages live at `/properties/<slug>` (slug made once by a DB trigger, never changed on title edits); `/property/<id>` only redirects there; build links with `propertyPath()` from `src/lib/propertySeo.ts`; why: one permanent readable URL per listing for SEO and sharing.
- Listing titles, meta descriptions, alt text, JSON-LD and the SEO completeness score come only from `src/lib/propertySeo.ts`, using real listing fields; why: one place that never invents specs and keeps pages unique.
- Popularity/trending lists come only from the `get_property_rankings` RPC fed by `record_property_view` (deduped, bot-filtered) plus favorites, share events and inquiries; why: rankings must be hard to game and consistent everywhere.
- Public listing visibility is enforced in the database: the `properties` public SELECT policy requires approved + active/published (+ non-demo unless `system_settings.show_demo_listings`), and `private.enforce_property_moderation` forces non-admin submissions/edits back to pending; service-role edge functions must repeat `approval_status='approved'` and `is_demo=false` explicitly; why: 170+ client queries read `properties`, so RLS is the only reliable boundary.
- Listing intake rules and admin review decisions come only from `src/lib/listingSubmission.ts` and `src/lib/listingReview.ts` (review notes in `properties.meta.review`, owner declaration in `meta.submission`; submitter phone stays on `profiles`); why: form, owner pages and admin queue must agree, and private contact data must never sit on a public row.
- Sample inventory is flagged with `properties.is_demo`; demo listings show a DEMO label, never claim "Verified", render noindex without listing JSON-LD, and are excluded from the sitemap, location-page counts and service-role searches; any sample generator must set `is_demo=true`; why: sample data must never be presented or indexed as real supply.
- Homepage search vocabulary (tabs → `/dijual`, `/disewa`, `/new-projects`; `location`, `type`, `price`, `beds` params; sale/rent price ranges) lives only in `src/lib/propertySearch.ts` and is read by `Properties.tsx`; why: the homepage and listings page must agree on every filter id.
- The ReosHeader primary row carries the marketplace nav (Beranda…Insight, Pasang Iklan, language, Masuk/Daftar); the REOS ecosystem tab row is hidden only on `/`; why: a compact marketplace homepage without losing module access elsewhere.
- Owner/agent/developer listing access comes only from an admin-approved row in `property_owner_requests` or `agent_registration_requests` (DB trigger `grant_role_on_approval` grants/revokes the role; `private.guard_role_request` forces new rows to pending); signup metadata is only a `profile_type` hint, and form rules/status live in `src/lib/listerOnboarding.ts` behind `/onboarding/listing`; why: clients must never grant themselves listing roles.
- Listing enquiries are rows in `inquiries` built by `src/lib/propertyInquiry.ts`; the `on_inquiry_created` trigger turns them into `property_leads` for the listing's agent (else owner), shown in My Properties; why: one lead path that RLS scopes to the listing's lister.
